# Linode / Akamai Cloud

MasterDNS binds and monitors existing public IPv4 and SLAAC IPv6 addresses. Automatic IPv4 rotation is supported only for a running Linode with **legacy configuration-profile interfaces**, exactly one configuration profile, Network Helper already enabled on that profile, normal (`default`) boot mode, and a simple public interface. An empty legacy `interfaces` array is the documented default public configuration. New Linode interfaces remain discoverable, with a distinct interface identity, but rotation is unsupported.

The operator must explicitly authorize downtime with `allowStop: true`. Rotation allocates an additional IPv4, reboots the verified configuration profile, observes successful completion, and then lets the existing external candidate health checks decide whether DNS can be updated. The original IPv4 stays assigned until DNS publication and separate release authorization. Cleanup consists of two independently persisted steps: release the exact original IPv4, then reboot again to remove the released address from guest configuration. Neither allocation nor a running control-plane status proves guest reachability. See [Network Helper](https://techdocs.akamai.com/cloud-computing/docs/automatically-configure-networking), [configuration profiles](https://techdocs.akamai.com/linode-api/reference/get-linode-config), and [managing IP addresses](https://techdocs.akamai.com/cloud-computing/docs/managing-ip-addresses-on-a-compute-instance).

## Credentials and permissions

Connect a personal access token. The authenticated `X-Customer-UUID` response header identifies the account; `/profile` supplies the authenticated username for reboot-event checks. Missing or changed customer identity fails closed. `X-OAuth-Scopes` records token permissions; `X-Accepted-OAuth-Scopes` is not used as permission evidence. Region selection comes from `/regions` and is separate from token permission scopes. MasterDNS never enumerates or creates access tokens. See [authentication](https://techdocs.akamai.com/linode-api/reference/get-started), [response headers](https://techdocs.akamai.com/linode-api/reference/response-headers), and [profile permissions](https://techdocs.akamai.com/linode-api/reference/get-profile).

For rotation, grant `linodes:read_write`, `ips:read_only` (or `ips:read_write`), and `events:read_only` (or `events:read_write`); wildcard `*` also satisfies the scope check. The token's user also needs permission to view the profile and operate the selected instance. Scope strings alone cannot establish effective user permissions or visibility. Read-only inventory can remain available when event observation is denied, but rotation will be unavailable. API permission failures are surfaced directly.

Additional IPv4 allocation requires support-approved quota and incurs charges. MasterDNS does not submit support tickets, transfer another instance's address, or create a substitute resource when quota is exhausted. The documented technical-justification rejection is reported as a quota failure. See [allocate an IPv4](https://techdocs.akamai.com/linode-api/reference/post-add-linode-ip) and [allocation limits](https://techdocs.akamai.com/linode-api/reference/post-allocate-ip).

## Safety and recovery boundaries

- Allocation is `POST /linode/instances/{id}/ips` with only `type: ipv4` and `public: true`. This legacy operation has no request idempotency token or writable attempt tag. Only a durable successful allocation response supplies candidate ownership evidence. A timeout, malformed success, or uncertain server failure stays **ambiguous**, including when fresh inventory shows zero, one, or several new addresses. Inventory differences never authorize another allocation or deletion.
- Reboot is `POST /linode/instances/{id}/reboot` with the exact verified `config_id`. Its empty success response means the reboot was requested. The persisted inventory/receipt contains an event watermark from before the write. Observation requires exactly one subsequent `linode_reboot` event for the selected Linode and authenticated username, a successful event status, unchanged configuration eligibility, exact candidate assignment, and a running instance. Missing events remain pending; multiple matches, unknown actors, and identity mismatches remain ambiguous. Failed events stop progression. Recovery never blindly repeats a reboot.
- Cleanup requires fresh publication/release authorization, the trusted original address ownership snapshot, and the known candidate allocation receipt. The original address must still belong to the selected instance and region; the published candidate must remain assigned. Current/published addresses, the final IPv4, mismatched ownership, and uncertain candidates are never released. A lost delete response is observed using exact inventory; when deletion is confirmed, the applied release receipt records a **fresh** event watermark. The subsequent cleanup reboot uses that receipt so the rotation reboot cannot be mistaken for cleanup completion.
- Linode exposes no per-allocation immutable generation identifier for this ordinary IPv4 path and no reboot request correlation token. The adapter checks exact assignment and saved evidence, but cannot prove absence of an external delete/reallocate cycle returning the same address to the same instance, or distinguish a concurrent reboot from the same user in every case. External concurrent changes are not protected by MasterDNS's internal instance lease. Do not operate this path concurrently with manual network or reboot changes. Multiple visible events and changed assignments are rejected conservatively; uncertain allocation still requires operator resolution.
- HTTP calls use a fixed API host, bearer authentication, manual redirect refusal, a ten-second timeout, bounded pagination, and no automatic mutation retry. Rate-limit delays are exposed to the caller. Logs/errors omit provider reason text and request credentials. No SSH, guest commands, profile edits, automatic Helper enablement, cross-instance assignment, or arbitrary address generation is performed.

See [reboot](https://techdocs.akamai.com/linode-api/reference/post-reboot-linode-instance), [events](https://techdocs.akamai.com/linode-api/reference/get-events), [event schema](https://techdocs.akamai.com/linode-api/reference/get-event), [delete IPv4](https://techdocs.akamai.com/linode-api/reference/delete-linode-ip), [pagination](https://techdocs.akamai.com/linode-api/reference/pagination), and [rate limits](https://techdocs.akamai.com/linode-api/reference/rate-limits).

## Unsupported rotation configurations

Helper disabled or unknown, multiple/unknown boot profiles, non-default boot mode, VLAN/VPC/multiple legacy interfaces, shared IPv4, routed IPv6 ranges, and new Linode interfaces do not qualify. The adapter does not turn Network Helper on: it can overwrite manual networking. New interface address updates have separate shutdown and replace-all semantics and require a different implementation. Reserved-IP lifecycle is also outside this implementation. See [update a Linode interface](https://techdocs.akamai.com/linode-api/reference/put-linode-interface) and [reserved addresses](https://techdocs.akamai.com/cloud-computing/docs/reserved-ips).

SLAAC IPv6 is hardware-derived and immutable for this purpose: MasterDNS can bind and monitor the actual global SLAAC host address, but cannot replace, remove, or transfer it. Link-local addresses and routed prefixes are never offered as candidates. Routed IPv6 ranges require guest address configuration; publishing an invented host from a prefix would not configure the guest. See [IPv6](https://techdocs.akamai.com/cloud-computing/docs/an-overview-of-ipv6-on-linode) and [managing addresses](https://techdocs.akamai.com/cloud-computing/docs/managing-ip-addresses-on-a-compute-instance).
