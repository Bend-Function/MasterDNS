# AWS 失败自动同步重置验证（2026-10-24）

## 要解决的问题

用户反馈原步骤恢复仍会反复卡住，实际可用的人工流程是“实例同步云端并重置本地状态，再开启 IP 自动轮换”。本次按该流程实现。代码基于已检查的 `5425a73` 工作树，替换 AWS 已开启自动轮换时的故障接续入口；其他厂商与未开启自动轮换的手动/定时任务继续使用原恢复路径。

原机制保留原 Incident、步骤计划及 unresolved 指针，恢复只能重读/重试同一步，即使实际云 IP 与本地任务进度已不一致也不会转入完整清单重建。新的 `RotationResetRecoveryService` 在 Processor、Publication observer、Cleanup scanner 三个入口接管失败；所有入口使用同一物理锁和状态标记，防止旁路继续原步骤。

## 实现与数据

- 从 API 提取 `db.resetCloudInstanceState`，手动和自动调用同一事务。新增 db 对 cloud-providers 的工作区类型依赖，锁文件无外部包版本变更。
- 自动同步先持久记账再调用云端，身份验证与清单读取共享最多 30 秒（或更小的配置值）。同步失败不修改清单/任务隔离，只记录错误、释放租约并延后；数据库/网络中断可再次调度。
- 成功读取后终止旧 Incident，放弃旧步骤和排队发布，清理本地 unresolved 指针，保留资源/回执/审计。以真实云 IP 重建版本并清空健康证据。自动路径恢复原来的开关值，不产生云写请求。
- 迁移 0035 新增 Slot `reset_recovery_retries`（0–20，默认 0）。新任务继承次数；默认最多 5 次同步尝试，包括同步失败，重启/重置/新任务 ID 不清零。健康独立发布/正常完成或显式手动同步重置结束预算链；单独切换开关不刷新预算。
- 历史终止及计费资源保留不代表远端删除。旧任务 UI 显示“已同步重置”，此状态不代表 DNS 已发布或旧资源已释放。
- 自动流程不能覆盖用户暂停、终止、关闭、撤权、修改配置或另一族已执行/被暂停任务。未准备 Attempt 的排队健康任务可共同重置，避免相互等锁。

## 证据与验证范围

第一条新增行为测试在旧 Processor 上失败，仍进入旧任务分支；接入同步重置后旧任务 complete/cloud_state_reset、实际新 IP 进入 candidateVersion 2，旧健康证据归零且开关保持开启。

独立审查找出了非自动任务被拦截、双地址族排队互锁、遗漏真实 ambiguity 错误码的问题，已补回归并修正。临时移除对应修复后四条回归均失败，恢复后通过。使用 `RotationStore.saveReceipt` 的真实持久路径产生 `resource_ownership_ambiguous`，不只测试人造错误字符串。

验证使用本地隔离 PostgreSQL/Redis、替身云清单/SDK；超时用例分别让身份适配器和清单 Promise 永久不返回，配置 10 秒后退出并释放租约。未连接真实 AWS/DNS，未执行生产同步重置或部署。历史验证记录中的数字保持其原有范围。

首次集成运行发现提取后的缺失导入和测试数据缺少主键，均修正并整组重跑通过。自动恢复入口作为独立编排器注入三个生产服务；既有不注入编排器的原步骤测试保留，用于验证非自动/其他厂商的底层恢复规则，新增集成用例显式注入编排器验证新 AWS 行为。

审查后取消了“只切换开关就刷新预算”的额外行为和承诺：版本隔离仍然有效，耗尽后的明确重启入口是现有手动同步重置。没有为恢复新增授权绕过。

最终独立只读复审确认前述问题已处理，代码与文档一致，无剩余阻止合入的问题；复审未重复执行上述测试。
