# MasterDNS 产品需求文档

| 项目 | 内容 |
| --- | --- |
| 版本 | 1.0 |
| 状态 | 已确认 |
| 产品类型 | 内部部署的多用户 DNS 运维平台 |
| 首批厂商 | Cloudflare、阿里云云解析 DNS |

## 1. 产品目标

MasterDNS 为内部用户提供统一的多云 DNS 管理、健康检查、动态 IP 上报和自动故障转移能力。系统直接执行 DNS 变更，所有人工和自动变更必须可观察、可追踪、可验证，并在满足安全条件时可回滚。

## 2. 非目标

首期不包含：

- 域名注册、续费、转移或交易。
- TLS 证书签发和管理。
- 权威 DNS 托管迁移。
- 复杂组织架构、审批流或细粒度资源共享。
- Telegram 内执行管理命令。
- ICMP Ping、DNS 查询、gRPC 或自定义脚本检查；这些只保留扩展接口。

## 3. 用户与权限

系统不开放自主注册。

### 3.1 管理员

- 创建、禁用、重置普通用户。
- 查看和操作所有用户的资源。
- 管理系统默认设置、数据保留和加密状态。
- 暂停或接管任意自动化策略。

### 3.2 普通用户

- 只能查看和操作自己的云账号、域名、IP Pool、DDNS Agent、告警渠道和历史。
- 可以创建、修改、启用、暂停和强制执行自己的自动化策略。

第一版使用用户名或邮箱加密码登录。密码使用 Argon2id 哈希；修改密码或禁用用户后撤销其全部会话。第一版不包含 OAuth、TOTP 和资源共享。

## 4. 云账号与 DNS 管理

### 4.1 云账号

- Cloudflare 使用最小权限 API Token，要求 Zone Read 和 DNS Write。
- 阿里云使用 RAM 用户 AccessKey，要求域名查询及记录增删改查所需的最小权限。
- 凭证加密保存，创建后不再回显明文。
- 接入时立即验证凭证、权限及可见域名。
- 展示最近同步时间、连接状态、权限错误和凭证轮换提示。

### 4.2 域名和记录

- 自动发现账号可访问的域名。
- 支持 A、AAAA、CNAME、MX、TXT、CAA、SRV 等厂商共同支持的记录类型。
- 支持查询、新增、修改、删除和批量同步。
- 保留厂商特有字段，例如 Cloudflare `proxied`，阿里云 `Line`、`Weight`、`Status`。
- 云厂商 API 是远端事实来源；MasterDNS 保存同步副本、期望状态和远端版本摘要。

### 4.3 配置漂移

- 未被自动化管理的记录在云厂商控制台发生变化时，接受远端值并记录“外部变更”。
- 自动化管理的记录以策略计算结果为期望状态。
- 检测到受管记录被外部修改或删除时，记录漂移、发送告警并重新应用策略。
- 用户必须先暂停或解除策略，才能让受管记录长期脱离策略控制。

## 5. 健康检查

健康检查通过可扩展的 Checker 接口实现，第一版提供 HTTP/HTTPS 和 TCP Connect 两种 Checker。

### 5.1 HTTP/HTTPS

- GET、HEAD 方法。
- 目标地址、端口、Path、查询参数及自定义请求头。
- 直接连接目标 IP，同时设置正确的 Host Header 和 TLS SNI。
- 期望状态码范围或列表。
- 响应体包含文本或正则匹配。
- 跟随跳转开关。
- TLS 证书验证开关。

### 5.2 TCP Connect

- 连接指定 IP 或域名及端口。
- 记录连接耗时。
- 超时、拒绝连接和网络错误均视为失败。
- 不使用 ICMP，不要求容器具有网络特权。

### 5.3 配置继承

- IP Pool 提供默认健康检查配置。
- 单个节点或域名绑定可以覆盖默认配置。
- DDNS Agent 在线只表示地址上报通道正常，不等于业务健康。

### 5.4 默认参数

- 检查间隔：15 秒。
- 单次超时：3 秒。
- 连续失败 3 次后判定故障。
- 连续成功 3 次后判定恢复。
- DNS 切换冷却期：5 分钟。
- 上一轮检查未结束时不启动重叠检查。
- 支持不受间隔限制的手动立即检查。

第一版由一个 Worker 执行检查；数据模型保留 Probe 标识和结果聚合边界，以便后续增加分布式探测点。

## 6. IP Pool 与自动故障转移

IP Pool 是自动化的统一资源模型，由节点、域名绑定、健康检查和调度策略组成。Pool 中的健康节点不限制承载域名数量。

### 6.1 策略类型

#### 主备模式 `primary_backup`

- 一个域名绑定多个有序节点。
- 主节点故障后选择健康备用节点。
- 修改受管 DNS 的值等同于修改主节点，并立即生效，策略保持启用。
- 修改备用节点必须在策略节点列表中明确操作。

#### 健康集合 `healthy_set`

- 一个域名发布全部符合条件的健康节点。
- 节点故障时从 DNS 记录集合移除，恢复后按恢复策略重新加入。
- 不能在普通 DNS 编辑器中独立修改记录值，必须编辑策略节点集合。

#### 跨域名分配池 `assignment_pool`

- 多个域名分别绑定池中节点，默认每个域名只发布一个活动节点。
- 一个节点故障时，当前由它承载的域名分别从其他健康节点中选择接管节点。
- 健康节点可以同时接管任意数量的域名。
- Cloudflare 和阿里云域名可以位于同一个 Pool。

### 6.2 调度方式

- 随机：从健康候选节点中随机选择。
- 顺序：按用户配置优先级选择第一个健康节点。
- 轮询：依次选择下一个健康节点。
- 最少分配：选择当前活动绑定最少的健康节点。

调度只在故障、符合配置的恢复、用户手动切换、节点变化或手动重新平衡时触发，不因每次健康检查重新分配。

### 6.3 恢复方式

每个 Pool 可选择：

- 自动恢复原节点。
- 保持当前节点。
- 等待手动恢复。
- 持续健康指定时间后延迟恢复。

如果新主节点当前不健康，系统保存配置但不发布该地址，继续保留当前健康节点；用户可以明确选择“忽略检查并强制生效”。

### 6.4 全池故障

- 保留当前 DNS 记录，不删除记录或制造 NXDOMAIN。
- 将 Pool 标记为“无健康节点”。
- 停止自动切换但继续健康检查。
- 立即发送告警，并在未恢复期间按配置重复提醒。
- 任意节点达到恢复阈值后重新调度。
- 允许用户选择节点并强制生效。

### 6.5 执行一致性

跨厂商操作不具备原子性。每条 DNS 修改作为独立步骤执行并展示 `pending/running/succeeded/failed` 状态。失败项单独重试，已经成功的步骤不盲目回滚。

## 7. DDNS Agent

DDNS Agent 绑定 IP Pool 节点，不直接绑定域名。节点分为静态节点和 DDNS 动态节点。

### 7.1 地址更新流程

1. Agent 上报新的 IPv4、IPv6 和主机信息。
2. 系统将新地址保存为候选地址。
3. 使用节点或 Pool 的健康检查验证候选地址。
4. 验证成功后提升为当前地址，并更新当前分配给该节点的 DNS 记录。
5. 验证失败时将节点标记为故障，由 Pool 调度其他健康节点。
6. 保存地址变化、健康结果、DNS 操作及通知历史。

### 7.2 Linux 一键安装

控制台为动态节点生成一次性安装命令。安装脚本需要：

- 创建低权限系统用户。
- 安装 Agent 到 `/usr/local/bin`。
- 将运行 Token 保存为权限 `0600` 的配置。
- 安装 systemd service 和 timer，默认 60 秒上报一次。
- 自动识别公网 IPv4/IPv6，并允许指定网卡或显式地址。
- 支持安装、状态、更新和卸载。
- 网络错误时退避重试，不阻塞系统启动。
- 一次性安装 Token 兑换为节点专用运行 Token 后立即失效。
- 运行 Token 只能上报对应节点，不能读取或修改其他资源。

## 8. 历史与回滚

- DNS 变更、策略版本和审计日志永久保留。
- 原始健康检查结果保留 30 天。
- 小时/天级健康统计保留 1 年。

普通记录保存修改前后值，可作为新操作回滚。自动化记录通过恢复旧策略版本并重新计算 DNS 回滚，不能只恢复单条云端记录。故障转移回滚到旧节点前必须检查该节点健康状态；不健康时默认拒绝，并提供明确的强制操作。

DDNS 地址变化仅提供历史查看。需要回退动态地址时，必须先停用 Agent 并将节点改为静态地址，避免下次上报再次覆盖。

## 9. 通知

### 9.1 事件

- 节点故障与恢复。
- DNS 自动切换成功或失败。
- 全池无健康节点。
- 自动恢复原节点。
- 云账号凭证失效或持续同步失败。
- DDNS 更新失败。

正常检查和成功但未变化的 DDNS 上报不发送通知。同一故障只在状态变化时立即通知；全池故障默认每 30 分钟重复提醒，恢复后发送恢复通知。

### 9.2 Webhook

- JSON 事件包含唯一事件 ID、时间、资源、状态及变更前后值。
- 使用 HMAC-SHA256 签名。
- 指数退避，最多重试 5 次。
- 保存每次投递的结果、响应码和耗时。

### 9.3 Telegram

- 配置加密保存的 Bot Token 和 Chat ID。
- 支持发送测试消息。
- 通知包含域名、故障节点、接管节点、检查摘要和控制台入口。
- 第一版仅发送通知，不在 Telegram 内执行管理命令。

## 10. 页面结构

- 概览
- 域名与解析
- IP Pool
- 健康检查
- DDNS Agent
- 云账号
- 变更历史
- 告警渠道
- 用户管理（仅管理员）
- 系统设置

界面以桌面运维场景为主。移动端支持查看状态、暂停策略和强制切换，复杂批量配置以桌面端为主。

## 11. 非功能需求

- 所有 DNS 写操作必须具备幂等保护、操作状态和远端读取验证。
- 自动化状态以 PostgreSQL 为准；Redis 不作为持久事实来源。
- API 和 Worker 日志不得包含凭证明文、Authorization Header 或敏感请求体。
- 所有用户资源查询必须包含资源所有权校验；管理员操作必须写入审计日志。
- Provider API 超时不能被直接解释为操作失败，必须查询远端确认结果后再决定重试。
- 系统重启后能够恢复未完成操作、检查计划和自动化状态。

## 12. 验收标准

- 管理员和普通用户的数据权限符合定义。
- 两类云账号均可接入、验证和同步。
- 普通记录 CRUD、历史和回滚可用。
- 三种 Pool 策略和四种调度方式得到确定性测试覆盖。
- HTTP/HTTPS/TCP 检查满足配置继承和阈值状态机。
- 全池故障不会删除当前 DNS。
- 动态节点地址变化可以驱动健康检查、分配和 DNS 更新。
- 外部修改受管记录后能够检测、告警并纠正。
- Webhook 签名、重试和 Telegram 通知可验证。
- Cloudflare 真实 API 的隔离记录 CRUD/回滚/清理测试通过。
