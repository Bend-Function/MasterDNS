# IP 定时轮换：调度设计

## 目标

在现有换 IP 策略上增加「每隔 N 分钟」触发，覆盖 AWS EC2/Lightsail、Azure VM 和 Linode 已支持的公网 IPv4 地址槽。服务商能力、授权、API 限制、尝试次数、复测、DNS 更新和旧 IP 清理由既有轮换策略及执行器决定。此次工作不新增按云商划分的验收模式，不修改适配器的换址步骤，也不扩展云商原本不支持的拓扑。

定时入口接入现有跨云轮换状态机；AWS 专用的 manual 快捷入口继续作为独立功能。当前代码中跨云入口要求 confirmed failure，因此接入定时功能需要小范围修改触发判断，不能把现有健康触发接口按时调用一下，也不能伪造故障证据。

## 用户配置

在现有机器轮换设置中增加独立的「定时轮换」区域：开关、正整数 N（分钟）、下次执行、最近任务及状态。默认关闭，默认间隔 1440 分钟（24 小时）；允许 1–129600 个整数分钟（最多 90 天）。定时开关控制到期启动，现有故障自动轮换开关继续控制故障启动，两者可以独立启用。

配置对象为地址槽，沿用当前机器列表、归属权限和已有换址设置。页面提供既有轮换策略的入口，不另建一套定时专用的尝试次数、复测或云商规则。现有执行条件不满足时展示执行器已有的阻塞原因。

## 时间与冲突规则

- 首次启用、重新启用、恢复日程或修改间隔：数据库当前时间加间隔；保存相同配置不重置倒计时。
- 成功完成：下一次时间为整个任务完成时间加 intervalMinutes × 60 秒，成功包括现有执行器要求的必要清理。手动或故障任务成功完成也推迟下一次定时任务，避免连续换址。
- 已有任务：同一地址槽的任何未完成任务均阻止新建定时任务；沿用物理实例租约处理跨地址槽冲突。
- 系统离线：恢复后到期日程最多接纳一次，不补跑历史各周期。
- API 限流、正常复测、云端收敛、TTL 等待：显示当前任务的等待状态，沿用执行器的重试和预算，不生成新任务。
- 任务暂停、耗尽或终止：日程暂停，显示既有原因。恢复日程不会自动恢复旧任务；旧任务仍未完成时继续显示冲突并阻止启动。
- 关闭日程：停止后续触发，不终止已接纳任务。进行中的任务仍由原有暂停／恢复／终止功能控制；后台完成处理不得重新开启已关闭的日程。

## 最小接入范围

新增 `rotation_schedules`，以 slotId 为主键：enabled、intervalMinutes、revision、nextRunAt、activeIncidentId、lastStartedAt、lastCompletedAt、lastHandledIncidentId、lastHandledIncidentUpdatedAt（内部字段）、pausedReason、updatedAt。revision 仅在用户配置变更时递增；lastHandledIncidentId 防止扫描反复用同一个历史完成事件重置计时。启用和修改配置时记录当前已知的最新完成事件作为基线。内部 lastHandledIncidentUpdatedAt 与任务 ID 一起记录已处理的暂停观察，明确恢复日程也消费该观察；同一任务在两次扫描之间恢复后再次暂停或终止仍会被识别，后续成功完成仍推进日程。普通队列唤醒仅推迟同一暂停／耗尽状态的 nextRunAt 时保留任务 updatedAt，避免把无状态变化的重试当作新暂停；真实状态、错误或执行结果变化仍更新时间。该时间戳不加入公开 API 响应；旧行的空标记在首次扫描时按未处理观察收敛。

新增 `GET/PATCH /v1/rotation-schedules/:slotId`，PATCH 接收 `{ revision, enabled, intervalMinutes }`；另以 `POST /v1/rotation-schedules/:slotId/resume` 接收 `{ revision }` 明确恢复已暂停日程，使用修订号避免重试重复重置倒计时。所有写入在事务内做归属和版本校验并记录审计。

`rotation_incidents.trigger` 增加 scheduled。scheduled 沿用现有跨云任务的健康配置版本、策略参数及任务预算；不再规定「定时只允许一次换址尝试」。一个到期事件只创建一个任务，但该任务内部允许多少次换址由当前轮换策略决定。scheduled 与 health 的差别限于启动条件：scheduled 核对有效日程、授权和既有执行前提，health 继续要求策略开启及故障证据。不能用关闭故障触发开关来否定已授权的定时触发。

调整 `rotation-store` 中「旧地址健康且尚未产生云写入则完成任务」分支，使该优化只适用于 health。scheduled 仍按既有正常路径产生候选地址、复测、发布、清理和收尾；其恢复、预算与健康配置版本处理沿用该路径。现有 manual 特殊路径保持原语义。数据库 CHECK 为 scheduled 保留与正常跨云任务一致的完整健康 epoch，不增加 verificationMode 或按云商新设默认验证条件。

新增调度服务只查询数据库，每 10 秒扫描一次；无排队及阻塞时，扫描发现到期的延迟约为 0–10 秒，不承诺精确到秒。扫描先处理关联任务状态与新的完成事件，再处理到期日程，按键分页限制每批 200 项，防止无效前缀阻塞其他日程。事务锁顺序统一为 `lockRotationContext` → schedule → incident；接纳时再次核对启用、暂停、版本、到期时间和已有任务。

来源事件使用 `scheduled-<revision>-<due UTC>`，在同一事务中创建既有格式的 incident 和预算、关联日程并清空 nextRunAt。事务提交后向现有轮换队列发唤醒；入队失败由现有恢复扫描补发，进程重启和多 Worker 不重复创建任务。执行中变更配置不改动已接纳任务；后续结果处理只更新仍然关联的日程，已关闭或已暂停状态不被后台解除。

## 验收标准

1. 三家服务商都可设置整数分钟间隔；健康的旧 IP 不阻止定时任务启动，故障触发仍要求故障证据。
2. 同等资源与策略下，定时触发与现有跨云执行使用相同的云步骤、预算、复测阈值、DNS 及清理条件；不增加定时专用云商规则。
3. 多 Worker、重复扫描、丢失队列消息和重启均不重复创建同一期任务；停机多个周期只补一次。
4. 现有任务、策略变更、权限撤销和限流按既有规则处理；日程关闭或人工暂停不会被后台扫描反转。
5. 本次只设计和实现调度接入；模拟适配器验收，不对真实云资源执行换址。
