# Manual AWS IPv4 rotation

The user requested a button to change IP once even while healthy and with no external probes, and explicitly chose to update bound DNS records too.

On the instance detail page, each supported AWS public IPv4 slot has a manual change action. A confirmation names the instance/current IP and explains one change, DNS update, no external reachability verification, and possible brief disruption. Submission is idempotent and opens durable progress. Existing managed/family authorizations remain required; the automatic rotation policy need not be enabled.

Persist a `manual` trigger on the existing rotation incident. A manual incident has a single-attempt budget and no fabricated health identity or evidence. Reuse existing cloud plans, leases, receipts, observation recovery and version checks. Do not start a second incident when another is active. A same-address candidate used only as the initial-verification placeholder does not block admission and its pointers and versions remain intact; a distinct pending candidate does block admission. Manual resume may continue the original operation, never grant another changed address after a charged attempt.

After cloud readback confirms the new address, publish it to bound DNS under explicit manual authority tied to this incident, slot, address version and authorization revision. Preserve automatic health gates for health-triggered incidents and ordinary binding publication. Do not persist healthy probe results for manually published addresses. No DNS bindings is a successful cloud-only completion. DNS failures remain visible and retry the DNS operation, never redo cloud allocation. Cleanup retains all ownership, reference and TTL gates. AWS IPv4 only in this delivery.

Acceptance: healthy/unconfigured/manual admission; disabled automatic policy; invalid/private/foreign/unauthorized rejection; same-key and concurrent idempotency; one cloud attempt; lost response observation; manual publication without probes including no links; DNS version/authorization guards and retry; unchanged automatic health behavior; visible button/confirmation/progress and pending duplicate protection. Use isolated databases and fake cloud transports, not real cloud mutations.
